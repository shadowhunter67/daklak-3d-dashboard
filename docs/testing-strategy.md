# Testing strategy

CI splits work into five jobs. `static-analysis`, `unit-and-data`, `build-and-budget`, and `security` start independently; `e2e` waits only for `build-and-budget`, downloads its `production-dist` artifact, and never rebuilds the application. Validation/build reports are uploaded even when their owning job fails where possible, and Playwright traces/screenshots are uploaded on E2E failure. GitHub Pages downloads the exact `dist` artifact produced by a successful `main` quality run instead of rebuilding it.

The required gate is `npm run quality`. It runs lint, formatting, strict TypeScript, Vitest, GIS validation, production build/budget, and production-preview Playwright.

Vitest covers manifest guards, build metadata, stores (including the reset-camera/help/insets-change signal counters that replaced a window-event bus), search normalization, geometry projection/hit testing, terrain uv-to-ward hit testing, 2D/3D road label building, administrative label layout, canvas geometry-path drawing, all generated label points, interaction performance, WebGL lifecycle cleanup, and the detail map (`src/components/detail-map/`): URL parse/serialize/clamp, the `FakeMapProvider` used in place of a real MapLibre instance, the lazy MapLibre/pmtiles loader's caching and retry behavior, distance measurement math, and the local search index. It also covers the project domain (`src/entities/project/`: validation, data-quality rules, KPI utilities, `assessPortfolio`), the Executive Overview read model (`buildExecutiveOverview`, deterministic for a fixed `asOf`) and every component under `src/features/executive-overview/` (KPI cards, priority list, alert grouping, data-health panel, loading/degraded/error states via `FakeProjectPortfolioSource`). Playwright smoke coverage runs on desktop Chromium (`Desktop Chrome`), mobile Chromium (`Pixel 7`), and desktop WebKit (`Desktop Safari`). Functional, accessibility, URL-state, and WebGL recovery tests run on all three profiles. Pixel baselines run only on desktop and mobile Chromium to avoid cross-engine rasterization noise. Production-only assertions verify hashed assets, lazy loading (including that the `maplibre-gl` chunk loads only when the detail map opens, and never alongside `AdministrativeMap`/`three-vendor`), and `build-info.json` once on desktop Chromium.

Executive Overview (Phase 2A) is the default landing (`?view=` absent, or the explicit canonical `?view=overview`); every pre-existing `?view=3d`/`?view=map` URL still resolves to exactly the view it always did. `?view=2d`/`?view=table` (the former standalone SVG+directory view) now alias to `?view=map`, the merged map+directory experience — see `docs/architecture.md`. Every E2E test that exercises these views navigates with the explicit param instead of relying on the old default. See the `Executive Overview (Phase 2A)` describe block in `e2e/dashboard.spec.ts` for landing, backward-compatible URLs, keyboard-only navigation to every primary destination, the project-summary dialog's Escape/focus-restore, stale-data disclosure, axe, and mobile no-overflow coverage.

The detail map's Playwright coverage runs against the **real** `MapLibreProvider`, not the fake one — `VITE_DETAIL_MAP_PROVIDER` is only set to `fake` for Vitest/RTL component tests, which run in jsdom without WebGL. Since no real PMTiles/terrain/satellite source is configured in this repository, the E2E tests exercise the same disabled-with-explanation states a real deployment would show until a real source is wired up (see [docs/detail-map-integration.md](detail-map-integration.md)) — they do not (and cannot yet) verify real road/boundary rendering.

Failed E2E traces and screenshots are uploaded by CI. The `quality` workflow never bootstraps or auto-generates a missing visual baseline: a pull request with no committed Linux baseline for a `toHaveScreenshot` assertion fails the same way a real visual regression would. CI failures must be fixed; tests and budgets must not be weakened to make a change pass.

### Updating a visual baseline on purpose

Baselines are only ever updated by a human after intentional review. Run the **Visual baseline (manual)** workflow (`workflow_dispatch` on `.github/workflows/visual-baseline.yml`) from the Actions tab, optionally scoping it with a `--grep` pattern. It builds production, runs the affected visual tests with `--update-snapshots` against `playwright.prod.config.ts`, and uploads the regenerated Linux `*.png` files as a downloadable artifact — it never commits, pushes, or merges anything. Download the artifact, replace the corresponding files under `e2e/dashboard.spec.ts-snapshots/`, review the diff as you would any other change (confirm the difference is the intended UI change, not a regression), and commit it through the normal PR flow. Locally, `npm run test:e2e:update` remains available for the same purpose against a dev build, but Windows/macOS baselines are never used for the Linux CI comparison — only the workflow (or a Linux machine) produces a baseline CI will actually match.

Manual release checks: latest Chrome/Safari hardware, keyboard-only traversal, 200% zoom, forced WebGL loss, low-power mobile responsiveness, external source links, and the deployed GitHub Pages URL.

Dependabot Three.js/R3F/Drei and Playwright/testing groups receive the same full quality workflow, including Chromium visual baselines. Major dependency changes are never auto-merged and require explicit review.

**Offline importer testing (Phase 4-5):** `scripts/import-data/` has its own Vitest suite (`npm run test:project-data-import`, wired into `quality:frontend`), covering CSV parsing edge cases (quoted/escaped/BOM/CRLF), normalization boundaries, pipeline integration against real JSON/CSV fixtures, the reusable `validateCanonicalReferentialIntegrity` check, and the staging script (`stage_internal_portfolio_bundle.test.ts`, using real temp directories rather than mocked filesystem). `scripts/import-data/benchmark/run_benchmark.test.ts` is a complexity guard, not a timing threshold — it asserts a bounded time ratio between a 25-project and a 250-project synthetic dataset (catching an O(n²) regression) rather than an absolute millisecond ceiling, which would be flaky across CI runners. `npm run benchmark:import-data` runs the full 25/250/1000-project report manually (not part of CI).

**Layout overlap/overflow regression (accessibility-first upgrade, 2026-09):**
`e2e/layoutAssertions.ts` (`expectNoOverlap`/`expectNoHorizontalOverflow`) and
`e2e/layout-regression.spec.ts` (16 tests × 2 Playwright projects) assert
pairwise non-overlap of the header/brand/nav/KPI cards and the detail map's
floating header/sidebar-toggle/layer-panel buttons across a representative
viewport spread (320/390/768/1024/1280/1920px) — direct regression coverage
for two previously-live, human-reported overlap bugs. `src/components/
detail-map/wardLabelPlacement.test.ts` unit-tests the 102-label collision-
displacement engine deterministically (no MapLibre/WebGL needed), including
one test that runs all 102 real ward labels through the algorithm at once.

**Public projection engine testing (Phase 6):** `src/entities/project/publicProjection/` has its own Vitest suite (`npm run test:public-projection`) covering field-allowlist filtering, record-level classification override, FK-safe cascade/orphan-reference pruning, determinism (same input → same `projectedContentChecksum`, independent of `generatedAt`), input-immutability, and refusal to project `restricted`/`confidential` bundles. `scripts/validate_portfolio_data_mode.mjs`'s decision logic (`evaluateFindings`/`detectPresentSourceKinds`) is unit-tested (`scripts/validate_portfolio_data_mode.test.mjs`) as a pure function, independent of any real `vite build` — see [ADR 0009](adr/0009-public-projection-and-ui-review-gate.md). UI changes are additionally gated by an independent Codex CLI visual review (`docs/project-data-import/ui-review-process.md`) before merge — Playwright/axe/unit tests do not substitute for it.
